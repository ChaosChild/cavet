# Distribution

How cavet reaches a machine. Binaries, container images, installers, and the
registries and directories that list them.

Scope: artefacts and channels only. Announcements, articles and newsletters are
not in this document.

Status key: `[ ]` not done, `[x]` done, `[-]` deliberately skipped.

---

## 1. Build targets

### 1.1 CLI binaries

Five targets are already configured in `.goreleaser.yml`. One addition.

| GOOS | GOARCH | Why | State |
| --- | --- | --- | --- |
| `darwin` | `arm64` | Apple Silicon — the default developer machine | configured |
| `darwin` | `amd64` | Intel Macs, still a real share | configured |
| `linux` | `amd64` | CI runners, servers, WSL | configured |
| `linux` | `arm64` | ARM CI runners, ARM SBCs | configured |
| `windows` | `amd64` | The author's own platform; installers are `.ps1`-first | configured |
| `windows` | `arm64` | Near-free to add, small but growing | configured |

Deliberately out of scope: `386`, `freebsd`, `riscv64`. Add on request, not
speculatively.

- [x] Add `windows_arm64` to `builds[0].targets`

### 1.2 Engine image

The engine image ships Opengrep, Gitleaks and Trivy. Multi-architecture, built
with buildx.

| Platform | Why |
| --- | --- |
| `linux/amd64` | Everything else |
| `linux/arm64` | Apple Silicon Docker Desktop, ARM CI |

- [x] `docker buildx build --platform linux/amd64,linux/arm64` in the release workflow
- [x] Tag scheme as built (engine-spec deviation 8): `<version>-<variant>`,
      `<minor>-<variant>`, rolling `<variant>` (e.g. `0.1.0-core`, `0.1-core`,
      `core`); `core-<digest8>` / `full-<digest8>` alias retags unchanged.
      The CLI derives the minor from its own version; dev builds use the
      rolling tags.
- [x] `CAVET_ENGINE_IMAGE` default in the CLI points at the published image, not a local build

## 2. Signing and provenance

cavet is a security tool. Unsigned artefacts undercut the product before the
first run. This section is not optional.

- [x] **Checksums** — already configured (`checksums.txt`)
- [x] **Cosign keyless signing** as Sigstore bundles (`signs:` blocks in
      `.goreleaser.yml`: `cosign sign-blob --bundle` on the checksum file and
      on SBOM artifacts; certificate + signature combined in one
      `.sigstore.json`). OIDC identity from GitHub Actions, no key to manage.
      These bundles replace GitHub-native attestations — `attestations: write`
      is not needed and not granted.
- [x] **SBOM** per archive — GoReleaser `sboms:` block (`artifacts: archive`)
- [x] **Image signing** — `cosign sign` the engine image by digest in the
      release workflow's engine job
- [ ] Document verification in `README.md`: the exact `cosign verify-blob --bundle` and
      `cosign verify` commands a user runs before trusting a download

## 3. Release automation

Only `ci.yml` exists today. A release workflow is the prerequisite for
everything below.

- [x] `.github/workflows/release.yml` — triggered on `v*` tag, two jobs
- [x] Permissions as built: the `binaries` job gets `contents: write` +
      `id-token: write`; the `engine` job additionally gets `packages: write`
      (GHCR push). `attestations: write` is not needed — Sigstore bundles
      replace GitHub-native attestations.
- [x] Steps: `binaries` = checkout → setup-go → cosign-installer →
      goreleaser-action (`release --clean`); `engine` = docker login GHCR →
      dedicated buildx builder → multi-arch build/push per variant with the
      three tags → `cosign sign` by digest → write and commit
      `engine/digest.txt` back to main
- [ ] Tag `v0.1.0` only once the engine image is published and `cavet init`
      succeeds from a clean machine with no local build

**Release gate.** Do not tag, and do not list anywhere below, while the README
still instructs users to `docker build` the engine themselves. First run must
work from the published artefacts alone.

## 4. Distribution channels

Ordered by return. Items 4.1–4.4 should all be live at v0.1.0.

### 4.1 GitHub Releases

The source of truth. Everything else points here.

- [ ] Signed archives, checksums, SBOMs attached
- [ ] Release notes generated from the changelog, not autogenerated commit lists

### 4.2 pkg.go.dev / `go install`

Free, automatic, no account. Indexed on first request after a tag is pushed.

Install line: `go install github.com/ChaosChild/cavet/cmd/cavet@latest`

- [ ] Module path matches the repo (already correct: `github.com/ChaosChild/cavet`)
- [x] Package-level doc comment on `cmd/cavet` so the pkg.go.dev landing page is not empty
- [ ] Verify listing after the first tag: <https://pkg.go.dev/github.com/ChaosChild/cavet>
- [x] Confirm `-X ...internal/cli.version` still populates for `go install` builds
      (it does not — ldflags are release-only; `resolveVersion` falls back to
      `runtime/debug.ReadBuildInfo`)

### 4.3 Homebrew — personal tap

`homebrew-core` is out of reach for a fresh v0.1.0. Their
[Acceptable Formulae](https://docs.brew.sh/Acceptable-Formulae) rules require a
stable, notable upstream; the notability thresholds are under revision. Tap now,
core later if it earns it.

Install line: `brew install --cask chaoschild/tap/cavet` (prebuilt binaries are
casks; goreleaser v2 deprecated `brews:` in favour of `homebrew_casks:`)

- [ ] Create repo `ChaosChild/homebrew-tap` (public, empty)
- [x] Add a `homebrew_casks:` block to `.goreleaser.yml` pointing at it
      (`binaries: [cavet]`)
- [ ] Personal access token with write access to the tap repo, as a secret in
      the cavet repo (GoReleaser needs to push the cask)
- [ ] Verify `brew install --cask` on a clean machine

### 4.4 Scoop — personal bucket

Matters more than usual here: Windows is the author's platform.

Install line: `scoop bucket add chaoschild https://github.com/ChaosChild/scoop-bucket` then `scoop install cavet`

- [ ] Create repo `ChaosChild/scoop-bucket`
- [x] Add a `scoops:` block to `.goreleaser.yml` (manifest committed to the
      bucket root — `directory:` left unset)
- [ ] Verify on a clean Windows machine

### 4.5 Container registry

- [ ] Publish the engine image to **GHCR** (`ghcr.io/chaoschild/cavet-engine`)
      — no pull rate limits, same auth as the repo
- [ ] Optionally mirror to Docker Hub, but document GHCR as the canonical one
- [ ] Make the package public (GHCR packages default to private)

### 4.6 Not doing yet

- [-] `nfpm` (.deb / .rpm) — cavet installs on developer machines, not servers.
      Revisit if CI-runner installs become a real use case.
- [-] `winget` — meaningful manifest review overhead for a pre-1.0 tool.
- [-] `homebrew-core`, `nixpkgs` — after traction, not before.

## 5. Harness installers

Seven harnesses are supported today via `installers/*.ps1` and `*.sh`:
`claude-code`, `codex`, `opencode`, `pi`, `hermes`, `zcode`, `deepseek`.

- [x] Installers fetch a released version rather than assuming a local clone —
      `installers/fetch.sh` / `fetch.ps1` resolve the version (default: latest,
      via the GitHub API), download the tag tarball, extract to a temp dir, and
      delegate to `installers/<harness>.<sh|ps1>` from there
- [x] Each installer prints what it wrote and where, and is idempotent on re-run
- [ ] `installers/README.md` path table verified against each harness's current
      config location before release

### 5.1 Claude Code plugin packaging

Worth doing as a separate distribution form, because it is the entry ticket to
the official directory (§6.1) and collapses install to one command for the
largest harness.

Required layout:

```
cavet-plugin/
├── .claude-plugin/
│   ├── plugin.json       # required manifest
│   └── marketplace.json  # the repo doubles as its own marketplace
├── skills/               # the six cavet-* skills
├── agents/               # cavet-security subagent
└── README.md
```

- [x] Add the plugin manifest and layout (a shuffle over existing assets)
- [x] **`name` is immutable once published** — it breaks existing installs if
      changed. Chosen: `cavet`, with `displayName` for the UI label.
- Marketplace mechanics (no `strict:` field exists — that note was wrong):
      the repo itself becomes a marketplace via
      `.claude-plugin/marketplace.json` listing the plugin with
      `source: "./."`; users run `/plugin marketplace add ChaosChild/cavet`
      then `/plugin install cavet@cavet`.
- [ ] The plugin must still require the `cavet` binary — document the dependency
      in its README rather than pretending the skills work alone

## 6. Registries and directories

Reviewed, first-party, and the discovery surface for Claude Code plugins.

- Repo: <https://github.com/anthropics/claude-plugins-official>
- Submission form: <https://clau.de/plugin-directory-submission>
- Requires: the plugin layout in §5.1, a README, and passing their quality and
  security review
- [ ] Submit after §5.1 is done and v0.1.0 is tagged

### 6.2 console.dev — best effort-to-reach ratio

Free weekly devtools newsletter with an explicit **beta section for pre-1.0
tools** — semantic versioning below 1.0 qualifies on its own.

- Criteria: <https://console.dev/selection-criteria>
- Submission: email `hello@console.dev` with the details. Free; editorial
  selection is separate from their advertising.
- [ ] Email after the release gate (§3) clears

### 6.3 Community directories

Low effort, PR- or form-based. Do these in one sitting.

- [ ] <https://claudemarketplaces.com> — plugin and skills directory

- [ ] `awesome-devsecops` — PR
- [ ] `awesome-go` — has strict inclusion criteria (repo age, tests, docs);
      check before spending the PR

Free discovery, five minutes, frequently forgotten.

- [ ] Repo description — one sentence, the same one as the README's opening line
- [ ] Topics: `claude-code`, `agent-skills`, `ai-agents`, `devsecops`, `sast`,
      `security-scanning`, `golang`, `mcp` *(only if an MCP surface ever exists)*
- [ ] Social preview image (1280×640) — shows in every link unfurl
- [ ] Release badge, licence badge, Go report card in the README

## 7. Order of operations

1. `windows_arm64` target, cosign, SBOM, release workflow (§1–3)
2. Publish the engine image to GHCR; make `cavet init` work with no local build
3. Tag `v0.1.0`
4. Verify: `go install`, then tap, then bucket, on clean machines
5. Repo metadata (§6.4) — before anyone arrives, not after
6. Claude Code plugin packaging (§5.1)
7. Submit: Anthropic directory, console.dev, community lists (§6.1–6.3)

Nothing in §6 happens before step 4 passes. A listing that leads to a broken
first run is worse than no listing.
